# ループBGMメーカー作成指示書 v0.2（叩き台）

- 状態: 叩き台（2026-11-13、v0.2）。未公開。付録Aの推奨案は 2026-11-13 に確定し本文へ反映済み。法的整備（§10）は同日のユーザー指示「著作権侵害やその他の法的整備は重要視して進める。リスクがないように」に基づき章として追加した
- 正式名称: ループBGMメーカー／英語名 Loop BGM Maker／リポジトリ名 `loop-bgm-maker`（A2で確定）
- 想定読者: この指示書だけを読んで、同等のメーカーを作成する Claude／Muse（対象製品についての前知識は前提にしない）
- 配布形態の想定: OSS。アプリ本体ではなく本指示書とテスト一式をリポジトリに置き、利用者側のエージェントが再現作成する（Encadraフレームメーカーと同形式）
- 前提の型: テーマ入力／プリセット選択／決定論的な後処理／自動検証／決まった形式での書き出し、の5点セット

## §0 目的と前提

- 本メーカーは、動画・ゲーム・配信向けの「継ぎ目のないループBGM」と、短い効果音・ジングルを作成するツールである
- 方式の核: **AIは音声を一発生成しない。AIは譜面データ（§4のJSON）を作り、プログラムがそれを音にする。** これにより、パート単位の修正（ベースだけ作り直す、テンポだけ変える等）と、完成形の自動検証（§8）が可能になる
- 実行環境: Webブラウザで完結するWebアプリ（想定はAIが生成する単一のWebアプリ／Space）。音の合成は Web Audio API 等のブラウザ標準技術で行い、外部の音声生成APIや素材ファイルに依存しない（自己完結。サンプルドラムも§2のとおりプログラム生成する）
- 対象外: DAWの代替、実楽器の忠実な再現、歌もの・ボーカル、既存曲の再現・模倣、長尺の楽曲（ループ素材と短いジングルに限る）
- テスト同梱の原則: 本指示書には§8のテストを同梱し、メーカーの新規作成時とバージョンアップ時にテストを実行する。不合格の場合は作り直し（最大3回）、同一の失敗が2回続いたら作業を止めてユーザーにバグ内容を報告し、修正提案を行う

## §1 入力

生成フォームの入力項目は以下とする。未指定時の既定値も併記する。

| 項目 | 内容 | 既定値 |
|---|---|---|
| テーマ／用途 | 自由文（例：森のRPGの街、作業用、戦闘）。曲の題材と雰囲気の指定に使う | なし（必須） |
| モード | §2の4モードから1つ | スタンダード |
| テイスト | §3のプリセットから1つ。モードの上に重ねる曲調指定 | 落ち着いた |
| BPM | 40〜200。テイストごとに推奨範囲を持ち、範囲外は警告する | テイストの中央値 |
| 調（キー） | 長調／短調の主音指定、または「おまかせ」 | おまかせ（AIが決めて譜面データに記録） |
| 小節数 | 4／8／16 から選択。ループの長さはBPMと小節数で一意に決まる | 8 |
| 拍子 | v1は 4/4 固定（3/4等は付録Aの後続候補） | 4/4 |

- 生成は「テーマ＋モード＋テイスト＋数値条件」を入力として、§4形式の譜面データを1曲分作ることから始める。音はまだ作らない

## §2 モード定義

モードは「編成と音源の制約」の定義である。モードごとに作曲ルールと検証方法が変わる。曲調（テイスト）とは混同しない。

### 2.1 スタンダード（既定）

- パート構成: メロディ／コード（和音）／ベース／ドラムの4パートを基本とし、任意でアルペジオ等の補助パートを足してよい（上限8パート）
- 和音はコードパート内でのみ可。各パート単独での音域・音量の目安は実装側で定めるが、上限パート数と「ベースは単音（同時に2音以上鳴らさない）」は検証対象とする
- 楽器セットは全合成の固定8種で確定する（A4）: ピアノ系／エレクトリックピアノ系／シンセリード／ベル／弦パッド／シンセベース／アコースティックベース風／合成ドラムキット。サンプル素材は使わない。楽器の追加はv2以降
- 汎用の受け皿。動画BGM・作業用など、特定の制約を求めない場合の既定

### 2.2 レトロ（Game Boy方式 4ch）

- 同時4チャンネル、各チャンネル単音（同時に2音以上鳴らさない）厳密:
  - CH1: パルス波（デューティ比 12.5%／25%／50%／75% から選択可）。スイープ（音程の滑走）はCH1のみ可
  - CH2: パルス波（スイープ不可）
  - CH3: 波形メモリ音源。波形はプリセット（正弦波寄り／三角波寄り／鋸波寄りを離散化したもの等）から選択し、ベースを主に担当
  - CH4: ノイズ。ドラム担当（短いノイズ＝ハット系、長いノイズ＝スネア系、のように長さとフィルタで打ち分ける）
- 和音は作れないため、和声はアルペジオ（分散和音）で表現する
- 拡張（いずれも既定OFF、固定2種のみ。自由にチャンネルを増やす拡張は作らない）:
  - **拡張1「三角波ベース」**: CH3を三角波に切り替える（追加ではなく切替）。ベースが安定しファミコン寄りの響きになる
  - **拡張2「サンプルドラム」**: DPCM風のサンプル再生1chを追加する（CH5）。サンプルは外部素材を使わず、キック／スネア等をプログラム生成したプリセットのみ
  - 両方ONの構成は「ファミコン相当」（パルス×2＋三角波＋ノイズ＋サンプル＝5ch）と表示してよい
  - 拡張の状態は譜面データのメタ情報と書き出しファイル名に必ず記録し、§8の検証ルールは拡張状態に応じて切り替える
- サンプルドラムのプログラム生成レシピ初期値（A5で確定。数値は初期値であり、受け入れ基準は「聴いて各楽器と判別できること」とする）:
  - キック: サイン波を約120Hz→45Hzへ0.12秒で下降、全体0.25秒
  - スネア: ノイズ（バンドパス約1800Hz）＋190Hzの短いトーン、全体0.18秒
  - ハット: ハイパス約8000Hzのノイズ、閉0.05秒／開0.3秒
  - DPCMらしさは、生成後にサンプルレートとビット深度を落とす処理（初期値 約16kHz／7bit相当）で付ける。外部サンプルは一切使わない（§10）

### 2.3 ピアノソロ

- パート数は1（検証対象）。ただし譜面データ内では右手／左手を2つの声部（voice）として分けてよい（音源は同一のピアノ系1種）
- ドラム・ベース等の他パートは持たない。伴奏とメロディを1台分に収める編曲がモードの個性である
- 音源の再現度の線（A4で確定）: サンプルは使わず、倍音＋減衰エンベロープの合成で「ピアノと分かる」水準を狙い、生演奏の再現とはうたわない。らしく聞かせる要素は音源ではなく作曲側（強さのばらつき、左右の声部の独立）に寄せる
- 用途想定: 作業用、配信、ナレーションの裏など、音が邪魔にならないBGM

### 2.4 アンビエント

- パート構成: パッド（持続する和音）が必須、任意で疎らなメロディと低いベース。ドラムは持たない（検証対象）
- BPMは 40〜90 を推奨範囲とし、コードの持続は2〜4小節単位を基本とする
- ループの継ぎ目対策として、ループ末尾を越えて伸びる音は先頭へ回して接続する（ラップアラウンド）ことをレンダリング仕様とする

## §3 テイスト定義

- テイストは曲調のプリセットで、モードの上に重ねる。各テイストは次のパラメータ束として定義する: 推奨BPM範囲／調の傾向（長調寄り・短調寄り）／コード進行の候補群／リズムの密度／モード別の音色マッピング
- 最終リストは12種で確定する（A1）: ポップ／ほのぼの日常／落ち着いた（lofi）／バラード／和風／ジャズ風／ロック／エレクトロニック／戦闘／神秘的／ダンジョン／ダーク／ホラー／壮大／冒険
- テイスト名は一般的な曲調の記述子のみを使い、作品名・ゲーム名・アーティスト名・商標を含めてはならない（§10の法的ルール。プリセット名も対象）
- テイストは組み合わせ（モード×テイスト）で増やす設計とし、モード自体は安易に増やさない

## §4 譜面データ形式

譜面データはJSONを正本とし、再生・編集・書き出し・検証はすべてこのデータを入力とする。

```json
{
  "meta": {
    "title": "森の街",
    "version": "0.1",
    "kind": "bgm",
    "mode": "retro",
    "taste": "calm",
    "bpm": 100,
    "key": { "root": "C", "scale": "major" },
    "bars": 8,
    "beatsPerBar": 4,
    "expansions": { "triangleBass": false, "sampleDrums": false }
  },
  "chords": [
    { "bar": 0, "chord": "C" },
    { "bar": 1, "chord": "G" }
  ],
  "tracks": [
    {
      "id": "ch1",
      "role": "melody",
      "instrument": "pulse",
      "duty": 0.25,
      "notes": [
        { "step": 0, "midi": 72, "len": 4, "vel": 0.8 },
        { "step": 4, "midi": 76, "len": 4, "vel": 0.8 }
      ]
    }
  ]
}
```

- 時間の単位は step（16分音符＝1 step、4/4の1小節＝16 step）。音符は開始step／音高（MIDIノート番号）／長さ（step）／強さ（0.0〜1.0）で表す
- コードは1小節に1つを基本とし、`chords` に小節番号とコード名で記録する
- モード・拡張・BPM・調・小節数と、生成に使った種（シード）は必ず meta に入れる。種は生成のたびにランダムに引くことを既定とし、譜面に記録して再現可能にする（同じ条件＋同じ種＝同じ曲、種が違えば人と被らない）。**生成時点で目標（モード・尺・構成）がデータに固定されることが、後の検証の前提である**（目標がデータに無いと、書き出しだけ正しくても中身のずれを検出できない、というフレームメーカーでの実例に基づく）
- 効果音のデータ形式は§6で別に定める（譜面形式とは分ける）

## §5 作曲ルール（AIが譜面データを作る際の規則）

共通:

1. まずコード進行を決め、`chords` に記録してから各パートを作る
2. メロディはコードトーンを骨格に、経過音でつなぐ。音域はモードの範囲内に収める
3. ベースはコードの根音を基本に、5度・オクターブで動きを作る
4. ドラム（持てるモードのみ）はテイストの密度に合わせたパターンを作り、全小節コピーではなく最終小節に小さな変化（フィル等）を入れてよい
5. ループ規則: 最終小節は冒頭のコードへ自然に戻る進行にし、メロディの最後の音が冒頭の最初の音へつながるよう配慮する。ループ末尾で音が不自然に切れる場合は、モードの仕様（アンビエントのラップアラウンド等）に従う
6. 既存曲のメロディの再現・引用はしない

パート別再生成:

- ユーザーはパート単位で「作り直し」「楽器変更」「ミュート」を指示できる。再生成時は指定パート以外とコード進行を保持する（コード進行自体の作り直しは別指示とする）
- 再生成でも §8 の検証を通らなければ採用しない

検証不合格時:

- 譜面データがモード制約（§2）や形式（§4）に違反した場合、AIは違反箇所だけを直して再提出する（全体の作り直しは最終手段）。試行回数の上限と報告の扱いは§0のテスト原則に準じる

## §6 効果音・ジングル編（同梱、ただし分離可能に作る）

- 本章の機能はBGM編とはモジュールを分け、テストも分ける。将来、効果音だけを切り出して単独のメーカーにできる構造にする（フォルダ・データ形式・書き出しを共有しすぎない）
- 効果音（SE）:
  - 対象カテゴリ: 決定／キャンセル／カーソル移動／成功・レベルアップ／失敗／ジャンプ／ヒット／コイン／場面転換、などシンセ系のみ。ドア音・足音等の実音系は対象外
  - 合成方式: 音程のスイープ（上昇／下降）、短いアルペジオ、ノイズバースト、の組み合わせで作る。各カテゴリに方式と長さの目安（0.05〜1.5秒）を持たせる
  - データ形式: 種類／長さ／方式／パラメータ（開始・終了音程、波形、カーブ）を記録する小さなJSONとし、BGMの譜面形式とは分ける
  - 書き出し時に音量を正規化し、頭の無音は詰める
- ジングル:
  - 2〜8秒程度の短い曲。BGMのモードを流用し小節数1〜2で作るが、ループさせず、最後は主和音で解決して終わる（BGMとの違いは「ループしない・解決する」の2点）
  - 用途: 場面転換、配信の開始・終了、動画の区切り

## §7 書き出し仕様

- 音声:
  - WAV: 44.1kHz／16bit。ループBGMの長さは「小節数 ×（240 ÷ BPM）秒」に一致させる（サンプル単位で丸め、誤差は§8の許容内）
  - MP3: 提供しない（2026-11-13 決定）。理由は、ブラウザ内エンコーダの定番ライブラリが LGPL で §10 の依存ライセンス方針に触れることと、MP3 は変換時の遅延でループの継ぎ目がずれるため本メーカーの目的に合わないこと。書き出しは WAV／MIDI／譜面JSON／ステムで完結させる
  - パート別ステム: パートごとのWAVを、全パート同一の長さで書き出す
- MIDI: 形式1（パート＝トラック）、テンポ情報を含む。譜面データから機械的に変換する
- 譜面JSON: そのまま保存・読み込みでき、読み込めば再編集と再書き出しができること
- ファイル名: `{タイトル}_{モード}_{BPM}bpm_{小節数}bar{_拡張サフィックス}.{拡張子}` を基本形とし、拡張サフィックスはレトロ拡張の状態を表す（例: `_xtri`、`_xsmp`、両方は `_xtri-xsmp`）
- アプリ内ギャラリー: 作成物は譜面データとメタ情報（モード／テイスト／拡張／BPM／調／小節数／作成日時）で保存し、一覧から再読み込みできること

## §8 検証テスト

検証は2層に分ける。(A) メーカー自体の作成・更新時に回すテスト（本指示書に同梱）、(B) 生成のたびにアプリが自動で行う runtime 検証。

(A)(B)共通の検査項目:

- T1 尺: 書き出した音声の実尺が、BPMと小節数から計算した目標尺と一致するか（許容誤差はサンプル丸め分まで）。**目標は生成時点の譜面データ meta を正とし、実測と比較する**
- T2 ループ継ぎ目: 波形の末尾と先頭の不連続が閾値以下か。あわせて譜面レベルで最終小節→冒頭のコード接続が成立しているか
- T3 音量: 無音でないか（RMSが閾値超。ただしアンビエントの静かな部分はモード別閾値）、クリッピングがないか（ピークが上限以下）
- T4 モード制約: チャンネル数／パート数、各チャンネルの単音性、音域、拡張状態と構成の一致（例：拡張OFFなのにサンプルドラムのトラックがある、は不合格）
- T5 譜面形式: JSONスキーマ妥当性、音符が小節範囲内に収まるか、単音トラックでの音符の重なりがないか
- T6 書き出し一式: WAV／MIDI／ステムの存在と、MIDIが読み戻せるか、ステムの長さが本体と一致するか（MP3は提供しないため対象外）
- T7 効果音: 長さがカテゴリの範囲内か、正規化されているか、頭の無音が詰まっているか
- T8 法的項目（§10.6）: 表示名・プリセット名に作品名／アーティスト名／商標が含まれていないか、デモ曲が新規生成のみか、依存物一覧とライセンスが揃っているか、READMEに注意表示と申立て窓口があるか

(A) の実行タイミングと不合格時の扱いは §0 のテスト原則どおり（作り直し最大3回、同一失敗2回で報告）。

## §9 画面と操作の流れ

1. **作成画面**: §1の入力フォーム（テーマ、モード、テイスト、BPM、調、小節数）と生成ボタン
2. **試聴画面**: ループ再生プレイヤー（継ぎ目が分かるよう最低2周再生できること）、曲情報の表示（モード／テイスト／拡張／BPM／調／小節数／実尺）
3. **編集部**: パート一覧。各パートのミュート／試聴（ソロ）／作り直し／楽器変更。レトロモードでは拡張トグル（切替時に検証ルールも切り替わる旨を表示）
4. **書き出し部**: §7の形式ごとの書き出しボタンと、検証結果（§8の合否）の表示。検証不合格のものは書き出しを止めるか、警告して理由を表示する
5. **ギャラリー**: 作成物の一覧、再読み込み、削除
- 実装環境がサイドバー等への設置をサポートする場合は、利用者が見つけやすい場所に置く指示を実装側で添えること

## §10 法的整備（リスク最小化の設計ルール）

本章は法的リスクを最小化するための設計・運用ルールであり、法的な安全を保証するものではない（偶然の類似など、設計だけでは消せないリスクが残るため、チェックと対応手順まで含めて1セットとする）。公開・運用にあたって疑義がある場合は、公開前に専門家（弁護士）へ確認する。

### 10.1 著作権（既存曲との類似の防止）

- 入力のスクリーニング: 特定の作品名・曲名・ゲーム名・アーティスト名を指定して「〜風に」「あの曲のように」と再現を求める入力は、そのまま作曲に使わない。一般的な属性（明るい、速い、和風の音階、等）へ変換するか、変換できない場合は再現依頼として受け付けない旨を表示する
- プリセットの作り方: コード進行・音階・リズム型は一般的な音楽手法の範囲で設計し、特定作品の特徴的な旋律やフレーズをプリセット・サンプル曲・デモ曲に含めない。デモ曲も全て本メーカーの規則で新規に作ったものだけを使う
- 生成ルール: §5の「既存曲のメロディの再現・引用はしない」を必須とし、生成されたメロディが自分の過去の生成物と実質的に同一になっていないかも併せて確認する（自己重複チェック）
- 効果音: 著名なゲーム等の効果音として広く知られた音の並び（特定の作品を想起させる音型）を再現しない。カテゴリ名・方式は一般的な記述に留める
